# Архітектура та принципи роботи навчального тренажера ЦП

Документ описує структуру, компоненти та логіку роботи інтерактивного навчального
тренажера задач лінійного та цілочислового програмування. Призначений як основа для
пояснювальної записки дипломного проєкту.

---

## 1. Загальна архітектура

Додаток побудований за **клієнт-серверною архітектурою** з чітким розділенням
відповідальності:

- **Frontend (клієнт)** — React-додаток у браузері користувача: відповідає за
  відображення інтерфейсу, інтерактивність, локальну статистику навчання.
- **Backend (сервер)** — Python/Flask REST API: реалізує самі алгоритми
  (симплекс, гілки і межі, метод потенціалів), валідатори дій студента, генератор
  випадкових задач, бібліотеку готових задач.
- **Комунікація** — JSON через HTTP/HTTPS. Жодного стану на сервері (stateless
  REST): кожен запит самодостатній.

Логічна схема:

```
┌─────────────────┐         HTTPS/JSON         ┌─────────────────┐
│                 │ ─────── POST /api ──────▶  │                 │
│  React (Vercel) │                            │  Flask (Render) │
│  TypeScript     │ ◀────── JSON response ──── │  Python         │
│  Ant Design     │                            │  NumPy / SciPy  │
└─────────────────┘                            └─────────────────┘
        │                                              │
        │                                              │
        ▼                                              ▼
   localStorage                                  data/tasks.json
   (статистика                                  (бібліотека готових
    навчання)                                    задач, read-only)
```

Розділення дозволяє:
- замінити фронтенд на іншу платформу (наприклад, мобільний додаток), не змінюючи
  логіку розв'язання;
- масштабувати або переписати алгоритми незалежно від UI;
- кешувати статичний фронтенд на CDN, поки сервер обчислень працює на іншій
  машині.

## 4. Серверна частина (Backend)

### 4.1. Точка входу — `backend/app.py`

Реалізовано шаблон **application factory** — функція `create_app()` створює і
конфігурує екземпляр Flask. Це дозволяє створювати окремі екземпляри для тестів
без побічних ефектів.

```python
def create_app() -> Flask:
    app = Flask(__name__)
    frontend_url = os.environ.get("FRONTEND_URL")
    if frontend_url:
        CORS(app, resources={r"/api/*": {"origins": frontend_url}})
    else:
        CORS(app)
    app.register_blueprint(api_bp, url_prefix="/api")
    return app
```

Особливості:
- **CORS налаштовується через env-змінну** `FRONTEND_URL`: у продакшні дозволено
  лише запити з домену Vercel; локально (без env) — будь-які origins.
- **Порт** береться з `PORT` (Render інжектить його автоматично), локально fallback
  на 5001.
- На рівні модуля створено `application = create_app()`, який потім підхоплює
  Gunicorn командою `gunicorn app:application`.

### 4.2. REST API — `backend/api/routes.py`

Усі маршрути зібрано у Flask Blueprint `api_bp` з префіксом `/api`. Перелік
ендпоінтів:

**Інформаційні:**
- `GET /api/health` — health-check
- `GET /api/algorithms` — список доступних методів
- `GET /api/stats` — заглушка статистики (фактична статистика — на клієнті)

**Бібліотека задач:**
- `GET /api/tasks?type=simplex|branch_and_bound|transport` — список задач за типом
- `GET /api/tasks/<id>` — деталі однієї задачі
- `GET /api/tasks/random?type=...` — випадкова задача з бібліотеки
- `POST /api/tasks/<id>/verify` — перевірка відповіді на задачу

**Генератор:**
- `GET /api/generate?type=...&vars=N&constraints=M` — згенерувати випадкову задачу

**Розв'язувачі (повертають покрокові розв'язки):**
- `POST /api/simplex` → таблиці кроків симплексу
- `POST /api/branch-and-bound` → дерево вузлів
- `POST /api/transport` → ітерації методу потенціалів

**Валідатори (для покрокового навчання):**
- `POST /api/simplex/check` — чи правильний обраний ведучий стовпець/рядок
- `POST /api/simplex/check-tableau` — чи правильно студент перерахував таблицю
  (сліпий режим)
- `POST /api/simplex/hint` — підказка для наступного кроку
- `POST /api/branch-and-bound/check` — чи правильна змінна обрана для розгалуження
- `POST /api/transport/check` — чи правильно побудовано план перевезень
- `POST /api/transport/check-potentials` — чи правильно обчислені потенціали u, v
- `POST /api/transport/check-entering` — чи правильно обрана клітинка для входу в
  базис

Усі ендпоінти суворо валідують вхідні JSON (наявність обов'язкових полів, типи
даних) і повертають структуровані помилки HTTP 400 / 500 з повідомленнями
українською.

### 4.3. Алгоритми розв'язання

#### 4.3.1. Симплекс-метод — `core/simplex_solver.py`

Класична реалізація **двофазного табличного симплекс-методу** для задач у формі:

```
min/max  c^T x
s.t.     A x ≤ b,  b ≥ 0,  x ≥ 0
```

Покрокова логіка:

1. **Стандартизація.** До кожного обмеження ≤ додається змінна відхилення `s_i ≥ 0`,
   утворюючи систему рівнянь. Якщо `maximize=True`, внутрішньо вектор цілі
   множиться на −1 (далі розв'язується мінімізація еквівалентної задачі).

2. **Побудова початкової таблиці** `T` розмірності `(m+1) × (n+m+1)`:
   - Рядки 0..m−1: коефіцієнти обмежень + одинична матриця змінних відхилення +
     стовпець b.
   - Рядок m: коефіцієнти цільової функції `c` + нулі + 0.
   - Початковий базис: `{s_1, ..., s_m}`.

3. **Snapshot кожного кроку.** Функція `snapshot(desc, p_row, p_col)` копіює
   поточну таблицю в історію кроків (для відображення на фронтенді). Для
   максимізації об'єктивний рядок при snapshot інвертується назад до оригінальної
   орієнтації.

4. **Перевірка оптимальності.** Якщо всі коефіцієнти рядка цільової функції ≥ 0
   (для мінімізації — у внутрішньому представленні), план оптимальний.

5. **Вибір ведучого стовпця (правило Данціга).**
   `p_col = argmin(obj_row[:n_total])` — стовпець з найбільш від'ємною
   приведеною оцінкою.

6. **Перевірка необмеженості.** Якщо всі елементи ведучого стовпця ≤ 0 →
   задача необмежена.

7. **Вибір ведучого рядка — правило мінімального відношення.**
   `θ_i = b_i / a_{i,p_col}` для всіх `a_{i,p_col} > 0`;
   `p_row = argmin(θ_i)`.

8. **Pivot-операція (Гаусове виключення):**
   - `T[p_row] ← T[p_row] / T[p_row, p_col]` (нормування ведучого рядка)
   - Для всіх інших рядків i (включаючи об'єктивний):
     `T[i] ← T[i] − T[i, p_col] · T[p_row]`

9. **Оновлення базису.** Змінна `p_col` замінює змінну `basic[p_row]`.

10. Повернення до кроку 4.

Після завершення витягується розв'язок: для кожної базисної змінної її значення
= відповідне b у таблиці; небазисні = 0.

Структура поверненого результату:
```python
{
    "status": "optimal",
    "solution": [x1, x2, ...],
    "optimal_value": float,
    "num_iterations": N,
    "steps": [
        {
            "description": "Початкова таблиця" / "Ітерація k" / "Оптимальна таблиця",
            "tableau": [[...]],
            "col_names": ["x1", ..., "s1", ..., "RHS"],
            "row_names": [...basic_var_names..., "z"],
            "basic_vars": [...],
            "pivot_row": int | null,
            "pivot_col": int | null,
        },
        ...
    ]
}
```

#### 4.3.2. Метод гілок і меж — `core/bnb_solver.py`

Реалізація **рекурсивного перебору з відсіканням** для цілочислових задач:

```
min/max  c^T x
s.t.     A x ≤ b,  x ≥ 0,  x ∈ Z^n
```

Алгоритм:

1. **LP-релаксація.** Відкидаємо вимогу цілочисловості, розв'язуємо звичайну ЗЛП
   за допомогою `scipy.optimize.linprog` (метод HiGHS).

2. **Обробка результату:**
   - **Недопустимий.** Якщо область допустимих розв'язків порожня → статус
     `"infeasible"`, гілка відкидається.
   - **Відсікання.** Якщо LP-значення ≤ поточного рекорду (для max) →
     `"pruned"`, гілка не може дати кращого результату.
   - **Цілий розв'язок.** Якщо всі змінні цілі → `"integer"`, оновлюємо рекорд.
   - **Розгалуження.** Інакше обираємо змінну з **найбільшою дробовою частиною
     (найближчою до 0.5)** — стратегія *most fractional branching*. Створюємо
     дві підзадачі:
     - Ліва: `x_j ≤ ⌊x_j*⌋`
     - Права: `x_j ≥ ⌈x_j*⌉`
     і рекурсивно викликаємо `_bnb` для кожної.

3. **Збір вузлів дерева.** Кожен вузол містить: ID, ID батька, мітку (додаткове
   обмеження), межі змінних, LP-значення, LP-розв'язок, статус, обрану змінну
   розгалуження. Це дозволяє фронтенду побудувати візуалізацію дерева через
   ReactFlow.

#### 4.3.3. Метод потенціалів (MODI) — `core/transport_solver.py`

Реалізація **класичного методу потенціалів** для збалансованої транспортної задачі:

```
min  Σ c_ij · x_ij
s.t. Σ_j x_ij = a_i  (запаси постачальника i)
     Σ_i x_ij = b_j  (потреби споживача j)
     x_ij ≥ 0
```

Етапи:

1. **Балансування.** Якщо ΣA ≠ ΣB, автоматично додається фіктивний постачальник
   або споживач з нульовими витратами.

2. **Початковий план — метод північно-західного кута.** Заповнення матриці з
   верхнього лівого кута: на кожному кроці `x_ij = min(залишок_запасу,
   залишок_потреби)`, далі переходимо вниз або вправо.

3. **Цикл методу потенціалів:**

   a. **Обчислення потенціалів `u_i`, `v_j`.** Фіксується `u_1 = 0`. Для кожної
      базисної клітинки виконується `u_i + v_j = c_ij`; послідовно розв'язується
      система для всіх потенціалів.

   b. **Перевірка оптимальності — обчислення оцінок.** Для кожної небазисної
      клітинки: `Δ_ij = c_ij − u_i − v_j`. Якщо всі `Δ_ij ≥ 0` → план
      оптимальний.

   c. **Вибір вхідної клітинки.** Клітинка з найменшим (найбільш від'ємним)
      `Δ_ij`.

   d. **Побудова замкненого циклу.** Через базисні клітинки знаходиться
      замкнутий контур, що починається з вхідної клітинки. Знаки чергуються:
      `+θ, −θ, +θ, −θ, ...`

   e. **Перерозподіл.** `θ = min(x_ij)` серед клітинок зі знаком «−». До клітинок
      «+» додаємо `+θ`, від клітинок «−» віднімаємо `θ`. Клітинка з вантажем `θ`
      і знаком «−» виходить з базису.

4. Повертаємось до кроку 3 до досягнення оптимальності.

Для кожної ітерації зберігається snapshot з матрицею перевезень, потенціалами,
оцінками, циклом, що дозволяє покроково відобразити процес.

### 4.4. Валідатори — `core/validator.py`

Шість функцій для перевірки дій студента у режимі покрокового навчання:

| Функція | Що перевіряє |
|---------|--------------|
| `validate_simplex_pivot` | Чи правильно студент обрав ведучий стовпець та рядок |
| `validate_simplex_tableau` | Чи правильно студент перерахував наступну таблицю в сліпому режимі (cell-by-cell, з вказівкою конкретних помилок) |
| `validate_bnb_branch` | Чи правильна змінна обрана для розгалуження (= найбільш дробова) |
| `validate_transport_allocation` | Чи коректно побудовано початковий план перевезень |
| `validate_transport_potentials` | Чи правильно обчислено `u_i`, `v_j` |
| `validate_transport_entering` | Чи правильно обрано клітинку для входу в базис |

Усі повертають уніфіковану структуру:
```python
{
    "valid": bool,
    "message": str,           # людино-читане пояснення
    "correct_col": int | None,
    "correct_row": int | None,
    "hint": str | None,       # підказка, якщо помилка
    "errors": [...]           # детальний перелік (для check-tableau)
}
```

### 4.5. Генератор задач — `core/generator.py`

Три функції:
- `generate_lp(vars, constraints)` — задача ЛП з випадковими коефіцієнтами в
  гарантовано допустимому діапазоні (всі b ≥ 0).
- `generate_ilp(vars, constraints)` — те саме для цілочислової задачі.
- `generate_transport(m, n)` — збалансована транспортна задача.

Дозволяє студенту тренуватися на необмеженій кількості нових задач без потреби
вручну вводити умови.

### 4.6. Бібліотека готових задач — `data/tasks.json`

Read-only JSON-файл зі структурованою колекцією учбових задач з вже відомими
відповідями. Кожна задача містить: тип, опис, дані задачі, очікувану відповідь.
Доступ через ендпоінти `/api/tasks*`.

## 5. Клієнтська частина (Frontend)

### 5.1. Точка входу та маршрутизація

**`src/index.tsx`** — рендер React-додатку в `#root`, обгортка в `BrowserRouter`.

**`src/AppRouter.tsx`** — основний layout:

### 5.5. Модуль симплекс-методу — `components/SimplexSolver/`

**`SimplexSolver.tsx`** — головний компонент:
1. Рендерить форму, кнопку «Розв'язати».
2. Викликає `solveSimplex(problem)`, отримує покроковий результат.
3. Показує картку з оптимальним значенням, розв'язком, кількістю ітерацій.
4. Перемикач «Крок за кроком / всі кроки»:
   - **«Всі кроки»** — компактний акордеон з усіма таблицями.
   - **«Крок за кроком»** — інтерактивний `<ProminentStep>` з квізом.

**`PivotCheck`** (всередині SimplexSolver) — інтерактивний квіз:
1. Фаза «col» — студент обирає ведучий стовпець з кнопок-варіантів. Відповідь
   валідується через `POST /api/simplex/check`. Адаптується під min/max (для max
   шукаємо найбільший додатний коефіцієнт; для min — найменший від'ємний).
2. Фаза «row» — таблиця відношень `b/a` (де `a > 0`), студент обирає рядок з
   мінімальним θ. Рядки з `a ≤ 0` вимкнені та мають tooltip.
3. Фаза «blind» (опційно) — `<BlindTableauInput>` пропонує самостійно
   перерахувати наступну таблицю.
4. Фаза «done» — результати показуються.

**`ProminentStep`** — центральний компонент кроку ітерації:
- Прогрес-бар із номером кроку.
- Картка «Поточний стан»: базис, значення ЦФ.
- Інтерактивний квіз `<PivotCheck>`.
- Після відповіді відкриваються пояснювальні блоки:
  - **Перевірка оптимальності** — таблиця оцінок (Δ_j), формулювання
    адаптоване під min/max.
  - **Вибір ведучого стовпця** — пояснення «чому саме цей».
  - **Вибір ведучого рядка** — повна таблиця мін. відношення з підсвічуванням
    рядка з мінімумом.
  - **🧮 Показати детальні обчислення pivot-операції** — згортуваний блок з
    компонентом `<PivotComputation>`.

**`PivotComputation`** — ключова педагогічна фіча: показує саму pivot-операцію
з підстановкою чисел у кожну клітинку:
- **Крок 3:** `R_pivot ← R_pivot ÷ pivot` — нормування ведучого рядка.
  Для кожної клітинки видно `старе ÷ pivot = нове`. Підсвічення — зелене.
- **Крок 4:** для кожного іншого рядка `R_k ← R_k − a_k · R_pivot`.
  Видно формулу з підставленим множником, далі результуюча таблиця, де кожна
  змінена клітинка показує `старе − a·нове_pivot = нове`. Підсвічення —
  жовте; pivot-елемент стає жирною «1»; легенда кольорів.

Обчислення робиться на основі поточної відображуваної таблиці (не залежить від
бекенду), тому самодостатнє і точно відтворює наступну таблицю.

**`SimplexTable`** — рендер симплекс-таблиці у вигляді HTML-таблиці з
підсвічуванням ведучого стовпця, рядка та pivot-елемента, легендою кольорів.

**`BlindTableauInput`** — поле для самостійного введення наступної таблиці.
Перевіряється через `POST /api/simplex/check-tableau`, який повертає список
конкретних помилкових клітинок.

### 5.6. Модуль методу гілок і меж — `components/BranchAndBound/`

**`BranchAndBound.tsx`** — головний компонент: форма (із додатковим блоком «Межі
змінних»), розв'язання, перемикач «вузол за вузлом / дерево».

**`BnBTree`** — візуалізація дерева через ReactFlow: кожен вузол — картка з
LP-значенням, розв'язком LP та статусом (Розгалуження / Цілочисельний /
Відсічено / Недопустимий) з відповідним кольором.

**`ProminentBnBStep`** — інтерактивний показ одного вузла:
- Картка з описом підзадачі (додаткове обмеження, межі змінних).
- LP-розв'язок із підсвічуванням дробових змінних.
- Квіз «яку змінну обрати для розгалуження?» — кнопки-варіанти,
  валідація через `POST /api/branch-and-bound/check`.
- Залежно від статусу вузла:
  - **«branched»** — після відповіді показується картка «🔀 Рішення:
    розгалуження» з таблицею порівняння дробових частин (з підсвіченою
    обраною) та двома картками «Ліва гілка / Права гілка» з обчисленням floor
    та ceil.
  - **«integer»** — картка «✓ Знайдено цілочисловий розв'язок!» з оновленням
    рекорду.
  - **«pruned»** — квіз «чи потрібно відсікти?», далі пояснення:
    `LP ≤ рекорд → відсікаємо`.
  - **«infeasible»** — інформативна картка про порожню область.

Логіка вибору — *most fractional branching* — пояснюється безпосередньо
таблицею: для кожної дробової змінної видно її значення, дробову частину та
відстань `|частка − 0.5|`; обирається з мінімумом.

### 5.7. Модуль транспортної задачі — `components/Transport/`

**`TransportSolver.tsx`** — головний компонент:
- Степери для кількості постачальників (m) і споживачів (n).
- Векторні поля для запасів A, потреб B.
- Матриця витрат C.
- Виклик `solveTransport(problem)` → результат з ітераціями.
- Картка з оптимальною вартістю, кількістю ітерацій, оптимальним планом
  перевезень (таблиця).
- Перемикач «крок за кроком / всі кроки».
- Інформаційне повідомлення, якщо задача незбалансована (додано фіктивного
  постачальника/споживача).

**`TransportTable`** — рендер таблиці одного кроку: підсвічення базисних,
вхідної клітинки, циклу; відображення u_i, v_j, оцінок Δ_ij.

**`ProminentTransportStep`** — центральний компонент кроку:
1. **Початковий крок** — пояснення методу північно-західного кута,
   алгоритм у вигляді списку, формула `m + n − 1`.
2. **Ітераційний крок:**
   - Блок «🔮 Потенціали u_i і v_j» — обчислені значення.
   - Блок «🔍 Оцінки небазисних клітин (Δ_ij)» — від'ємні оцінки виділено.
   - Квіз «🎯 Спробуй сам: яку клітину обрати для входу в базис?» — кнопки
     з усіма від'ємними клітинками + дистрактори (для невеликих задач), щоб
     завжди було ≥3 варіанти (детермінований перемішаний порядок).
   - Після відповіді: «📍 Вхідна клітина», «🔄 Цикл перерозподілу»
     з тегами `+θ / −θ`.
   - **«🧮 Показати перерозподіл по циклу»** — згортуваний блок з компонентом
     `<CycleComputation>`.
3. **Оптимальний крок** — повідомлення «Оптимальний план досягнуто!» з
   поясненням `Δ_ij ≥ 0`.

**`CycleComputation`** — педагогічна фіча для транспортної задачі: показує
нову матрицю перевезень з арифметикою кожної клітини циклу:
- Клітинки `+θ` (зелений фон): `старе + θ = нове`.
- Клітинки `−θ` (жовтий фон): `старе − θ = нове`.
- Клітинка, що **виходить з базису** (значення стало 0): червоний фон + позначка
  «(виходить)».
- Решта клітин не змінюється.
- Легенда кольорів.

**`PotentialsChecker`** — окрема навчальна панель «Тренування: обчисліть
потенціали та оберіть вхідну клітинку»:
- Інпути для введення `u_i`, `v_j` (поле `u_1` зафіксоване як 0).
- Кнопка «Перевірити потенціали» → `POST /api/transport/check-potentials` →
  показує конкретні помилки.
- Після правильних потенціалів — крок 2: інтерактивна таблиця для вибору
  вхідної клітинки → `POST /api/transport/check-entering`.

## 6. Педагогічна модель

Додаток побудований на принципі **активного навчання**: студент не пасивно
читає розв'язок, а самостійно приймає рішення на кожному ключовому кроці і
негайно отримує зворотний зв'язок.

### Прогресія складності для одного методу

1. **Режим «всі кроки»** — оглядовий перегляд готового розв'язку (для першого
   ознайомлення).
2. **Режим «крок за кроком»** — інтерактивний прохід, де на кожній ітерації
   студент:
   - сам обирає, що робити далі (ведучий стовпець/рядок, вхідна клітинка,
     змінна розгалуження);
   - отримує валідацію та пояснення помилок;
   - **бачить детальні обчислення** (нова фіча — блоки PivotComputation /
     CycleComputation / таблиця дробових частин), щоб зрозуміти не лише *що*
     робити, а й *як* саме перерахувати.
3. **«Сліпий» режим** (для симплексу) — найбільш складний: студент сам пише
   наступну таблицю від руки, додаток вказує конкретні помилкові клітинки.
4. **Тренування потенціалів** (для транспортної) — окремий блок, де студент
   самостійно обчислює `u_i`, `v_j`.

### Підтримка викладача

- Бібліотека готових задач (`data/tasks.json`) із заздалегідь відомими
  відповідями для контрольних занять.
- Генератор випадкових задач для індивідуальних завдань.
- Статистика спроб (на стороні клієнта) — кількість розв'язаних задач,
  середня кількість помилок.

### Адаптивність формулювань

Усі пояснювальні тексти у симплексі адаптуються до напрямку оптимізації:
- **min:** «найменший від'ємний коефіцієнт», умова оптимальності «всі Δⱼ ≥ 0»,
  «зменшити z».
- **max:** «найбільший додатний коефіцієнт», умова оптимальності «всі Δⱼ ≤ 0»,
  «збільшити z».

## 7. Потік даних (на прикладі симплекс-методу)

1. Користувач заповнює форму ЗЛП у `<ProblemInputForm>` і натискає «Розв'язати».
2. Викликається `solveSimplex(problem)` → `POST /api/simplex` з JSON-тілом
   `{c, A, b, maximize}`.
3. Flask приймає, валідує, передає у `core.simplex_solver.solve_simplex(c, A, b,
   maximize)`.
4. Solver проганяє алгоритм, на кожній ітерації викликаючи `snapshot()`, що
   копіює таблицю в історію `steps`.
5. Повертається JSON `{status, solution, optimal_value, num_iterations, steps}`.
6. Фронтенд отримує відповідь, рендерить картку з результатом.
7. Якщо увімкнено «крок за кроком» — створюється `<ProminentStep>` для поточного
   кроку.
8. Студент натискає «Перевірити стовпець» → `POST /api/simplex/check` →
   валідатор повертає `{valid, correct_col, hint}`.
9. Якщо правильно — рендериться фаза «row»; інакше — повідомлення з підказкою.
10. Після проходження повної ітерації студент натискає «Наступний крок» →
    `currentStep++`, ремаунт `<ProminentStep>` з новим кроком.
11. На останньому кроці виклик `recordAttempt({...})` → запис у localStorage.

Аналогічно для транспортної задачі та методу гілок і меж — змінюються лише
ендпоінти і компоненти кроку.

## 8. Розгортання (Deployment)

### Frontend → Vercel
- Git-push у `main` запускає автоматичний білд: `npm install` + `npm run build`.
- Білд-артефакти (HTML/JS/CSS) деплояться на глобальний CDN.
- `vercel.json` визначає **SPA-rewrites**: усі маршрути віддають `index.html`,
  далі React Router обробляє URL на клієнті.
- Env-змінна `REACT_APP_API_URL` запікається в JS-бандл на етапі білду.

### Backend → Render
- Git-push у `main` запускає білд: `pip install -r requirements.txt`.
- Старт: `gunicorn app:application --bind 0.0.0.0:$PORT --workers 1 --threads 4`.
- `render.yaml` у корені репозиторію автоматично конфігурує сервіс при імпорті
  (один клік у Render UI).
- Env-змінні:
  - `PORT` — інжектується Render автоматично.
  - `PYTHON_VERSION=3.12.4` — фіксує версію Python.
  - `FRONTEND_URL` — встановлюється вручну після першого деплою фронтенду для
    замикання CORS на конкретний домен.

### Особливості безкоштовних планів

- **Vercel hobby** — без обмежень для статичного контенту, миттєвий CDN.
- **Render free** — сервіс засинає після 15 хв простою; перший запит після сну
  ~30 с (cold start), далі швидко.

### Цикл розробки

1. Локальна розробка: `python backend/app.py` + `npm start` у `frontend/`.
2. `git commit && git push origin main`.
3. Vercel + Render автоматично перебілдять і задеплоять зміни (~2-5 хв).

## 9. Тестування та верифікація

### Юніт-тести
У `backend/tests/`:
- `test_simplex.py` — перевірка коректності розв'язку базових задач, граничних
  випадків (необмеженість, виродженість).
- `test_branch_and_bound.py` — порівняння з відомими цілочисловими оптимумами.
- `test_transport.py` — балансування, метод північно-західного кута, цикли.
- `test_validator.py` — перевірка валідаторів на правильні та хибні відповіді.
- `test_api_routes.py` — HTTP-рівень: статуси, формат відповідей.

### Інтеграційна верифікація
Незалежна звірка через `scipy.optimize.linprog` та `scipy.optimize.milp`:
розв'язувачі додатку прогнано на серії задач, оптимальні значення збігаються з
незалежним розв'язувачем у межах `1e-5`. Pivot-переходи симплексу, цикли
транспортної та вибір змінної у BnB перевірено на консистентність крок-за-кроком.

## 10. Підсумок

Додаток реалізує **навчальний інтерактивний тренажер** для трьох класичних
методів ЦП із трирівневою прогресією складності (пасивний перегляд → активний
вибір з валідацією → самостійне обчислення). Архітектура клієнт-сервер з REST
API забезпечує чітке розділення презентаційного шару та обчислювальної логіки,
що дозволяє незалежно розвивати UI та алгоритми. Деплой на безкоштовних
хмарних платформах робить додаток доступним 24/7 без обслуговування з боку
розробника.
